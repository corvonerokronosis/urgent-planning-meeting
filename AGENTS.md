# «Срочная планёрка» — инструкции для Codex

## 1. Назначение репозитория

Этот репозиторий содержит браузерную decision-game «Срочная планёрка» на React + TypeScript + Vite. Игрок проходит 12 стадий управленческой ситуации, принимает решения, меняющие четыре ресурса и отношения с персонажами, сталкивается с ветвлениями/отложенными последствиями/кризисами и получает один из итоговых профилей.

Работай по текущему запросу пользователя, сохраняй существующую модель данных и pure game-engine. Не расширяй scope игры или технологический стек без явной причины.

## 2. Источники истины и их приоритет

Используй источники в таком порядке:

1. Прямые инструкции пользователя в текущем треде.
2. `README.md` — актуальный feature set, стек, запуск и поведение текущей версии.
3. `docs/content-model.md` — контракт сценариев, choices, effects, conditions и контента.
4. `src/game/engine.ts`, связанные типы и `src/game/engine.test.ts` — формальные текущие правила игры и проверяемые инварианты.
5. `src/data/scenario.ts` и `src/data/characters.ts` — фактический игровой контент/баланс.
6. `src/game/useGameController.ts` — orchestration, history, progression, persistence и browser-side lifecycle.
7. `ТЗ_Срочная_планёрка.docx` — исходные продуктовые цели и базовые критерии приёмки.
8. `docs/gameplay-ui-ux-roadmap.md` — полезный UX-аудит и направления развития; не считай каждый пункт roadmap обязательной текущей задачей, если он не реализован и пользователь его не запросил.
9. React components/CSS — фактическое presentation behavior.

Если исходное ТЗ описывает более узкий vertical slice, а README/код уже фиксируют развившуюся версию, сохраняй текущие возможности, пока пользователь явно не попросил упростить их.

Не придумывай новые balance values, формулы, thresholds или narrative consequences как окончательные требования. Если существующие источники не дают решения, а без него нельзя корректно продолжить, вынеси вопрос пользователю. Технические детали внутри уже заданного поведения решай самостоятельно.

## 3. Экономное чтение контекста

Не читай весь scenario и все components по умолчанию.

Перед задачей:

- найди затронутый event/choice/flag/stat/character через `rg`;
- для правила сначала изучи релевантный участок `engine.ts` и ближайшие тесты;
- для persistence/lifecycle изучи только соответствующие функции controller;
- для UI найди component и связанные CSS selectors;
- к `gameplay-ui-ux-roadmap.md` обращайся только если задача UX/responsive/accessibility или пользователь прямо ссылается на roadmap;
- не исследуй `node_modules/`, `dist/`, coverage/output и Git internals без причины.

Для крупных scenario-файлов предпочитай поиск по ID и небольшие диапазоны.

## 4. Архитектурные границы

Сохраняй существующее разделение:

- `src/game/engine.ts` — pure game rules и вычисления, без React/DOM/localStorage;
- `src/data/` — сценарии, персонажи и контентные значения;
- `useGameController.ts` — orchestration сессии, progression/history и persistence;
- React components — отображение и пользовательские команды, без второй копии доменной логики;
- CSS — presentation, responsive и motion.

Не переносись к Redux/Zustand, backend, БД, серверной авторизации или новому UI-kit без отдельной необходимости.

Сохраняй текущие доменные инварианты:

- четыре основных stat (`deadlines`, `budget`, `team`, `client`) остаются в диапазоне 0–100;
- отношения с персонажами остаются в диапазоне 0–100;
- effects применяются через engine, а не вручную только в компоненте;
- условия `flag` / `all` / `any` / relationship / stat должны сохранять текущую семантику вложенных условий;
- выбор следующего event/stage должен учитывать условия и не создавать зависшую недостижимую стадию;
- delayed consequence сохраняет источник event/choice и срабатывает после заданного количества последующих событий по текущему контракту;
- история/итоговый разбор должны ссылаться на фактически сделанные choices и последствия;
- ending profile определяется итоговым state по engine rules и должен совпадать с отображаемым финалом;
- crisis recovery и challenge rules не должны обходить clamp/основной effect pipeline;
- restart создаёт новую чистую сессию и очищает актуальные/legacy persistence keys, которые текущий controller обязан удалять;
- localStorage format/versioning меняй как контракт: с миграцией/сбросом несовместимых данных и тестом ожидаемого поведения;
- analytics остаётся локальным browser-событием проекта, если пользователь явно не просит внешнюю аналитику; не добавляй отправку данных наружу заодно.

Текущий release рассчитан на 12 стадий за проход, содержит 15 configured events, ветвящиеся стадии и несколько итоговых профилей. Если задача меняет структуру progression, обновляй engine/tests/content/docs согласованно.

## 5. UI/UX и browser behavior

Сохраняй работоспособность на desktop и mobile. Для responsive/UI-задач учитывай текущую цель проекта:

- критические действия не выходят за viewport и не требуют горизонтального скролла;
- на узких экранах HUD остаётся читаемым;
- интерактивные цели пригодны для touch;
- увеличенный текст/zoom не скрывает основной flow;
- focus и keyboard navigation остаются понятными;
- `prefers-reduced-motion` учитывается там, где есть motion/transition;
- важное состояние и последствия не сообщаются только цветом или краткой анимацией.

Не выполняй визуальный редизайн всей игры из-за локальной UX-задачи.

## 6. Работа с задачей и Git

Перед изменениями:

1. Определи scope, критерий приёмки и затрагиваемые слои.
2. Выполни `git status --short --branch`.
3. Не перезаписывай несвязанные изменения пользователя.
4. Если это новая отдельная задача из чистого `main`, создай понятную ветку `feat/...` или `fix/...`; если уже открыта подходящая task-ветка, продолжай её.

Во время реализации:

- меняй минимальный набор файлов;
- сначала используй существующие helper/type/engine contracts;
- не выполняй следующую идею из roadmap заодно;
- не делай несвязанный component/CSS refactor;
- если меняется content schema, обновляй типы, validation/engine consumers, контент и тесты одним согласованным change set;
- не добавляй dependency, если задача решается текущим стеком.

Без явной команды пользователя не выполняй `git commit`, merge, rebase, reset, stash, удаление веток, `git push` или настройку remote.

## 7. Тесты и локальная проверка

Проверяй сначала узкую область, затем один раз полный набор перед handoff после обработки findings.

Для game-engine/scenario changes:

- запускай релевантный Vitest-файл/тесты, обычно `pnpm exec vitest run src/game/engine.test.ts` или более узкий pattern;
- добавляй или обновляй тест для изменённого правила;
- включай boundary cases, если меняется threshold/condition/timer/delayed count;
- проверяй restart/persistence отдельно, если они затронуты.

Для TypeScript/UI/integration changes выполни `pnpm build` хотя бы один раз после стабилизации реализации: build включает TypeScript project build.

После обработки независимых findings и перед передачей пользователю выполни:

- `pnpm test`;
- `pnpm build`;
- `git diff --check`.

Не повторяй полный test/build без изменения кода или конкретной причины.

Не изменяй тест только ради зелёного результата. Если ожидаемое поведение действительно изменилось по актуальному требованию, обновление теста должно отражать именно это требование.

## 8. Независимые subagents

После реализации и узких локальных проверок, но до финального handoff, используй project subagents.

### `reviewer` — обязательный

Для каждой нетривиальной задачи передай reviewer:

- текущий запрос и критерий приёмки;
- изменённую область;
- просьбу независимо проверить рабочую ветку относительно `main`, когда `main` является корректным baseline.

Не подсказывай ему, что именно «должно быть правильно». Reviewer read-only и должен искать regressions/bugs сам.

### `logic_auditor` — только для rule-bearing changes

Запускай, если задача меняет:

- stat/relationship effect values;
- clamp/limit/threshold;
- branch/condition semantics;
- next-event progression;
- delayed consequence count/trigger;
- crisis/timer/challenge rule;
- ending formula/profile selection;
- quantitative result/review logic;
- persistence rule, если оно влияет на восстановленный игровой state.

Не запускай его для чистой перестановки уже рассчитанных чисел в UI.

Reviewer и logic_auditor могут работать параллельно.

### `ui_qa` — единственный владелец независимой финальной browser QA

Запускай `ui_qa`, если задача изменяет component, CSS, тексты/feedback в пользовательском flow, interaction, timer display, result/review, persistence/resume UI или другое видимое browser behavior.

До `ui_qa` основной implementing agent может запускать dev/browser для разработки и устранения явных проблем. Финальную независимую проверку changed flow, desktop/mobile, console, keyboard/accessibility и реального state change делегируй `ui_qa` и не дублируй её после успешного результата.

Если `ui_qa` нашёл подтверждённый finding, implementing agent исправляет его. Затем `ui_qa` повторно проверяет только затронутый flow, если исправление не расширило область риска.

Если `ui_qa` технически не может запустить приложение/браузер, основной agent может выполнить fallback browser QA сам, но обязан явно отметить это в итоговом отчёте.

Все custom subagents не изменяют репозиторий.

## 9. Работа с findings

BLOCKER:

- не передавай результат пользователю;
- исправь;
- повтори релевантные автоматические проверки;
- повторно вызови соответствующего subagent по исправленной области.

HIGH:

- исправь подтверждённую техническую проблему до handoff;
- если finding является незафиксированным product/design choice, вынеси решение пользователю.

MEDIUM/LOW исправляй, когда это относится к текущему scope и не создаёт отдельный рефакторинг. Иначе перечисли как остаточные findings.

Перед handoff не должно быть подтверждённых неразрешённых BLOCKER/HIGH.

## 10. Документация

Обновляй документы по назначению:

- `README.md` — если изменился актуальный feature set, запуск или публично важное поведение;
- `docs/content-model.md` — если изменился контракт контента;
- `docs/gameplay-ui-ux-roadmap.md` — только когда пользователь меняет сам roadmap/статус рекомендаций либо задача прямо требует его актуализировать;
- исходное DOCX-ТЗ не переписывай из-за обычной реализации без прямого запроса пользователя.

Не создавай отдельный status/backlog tracker только ради процесса Codex, если пользователь этого не просил.

## 11. Финальный отчёт

После реализации кратко сообщи:

- что сделано;
- результаты `pnpm test`, `pnpm build`, `git diff --check` и релевантных узких тестов;
- как пользователю вручную проверить критерий;
- `Независимое ревью`: какие subagents запускались, были ли BLOCKER/HIGH, что исправлено после findings, какие MEDIUM/LOW остались;
- известные ограничения/блокеры.

Не называй задачу окончательно завершённой и зафиксированной в Git, пока пользователь не подтвердил результат и не попросил нужную финализацию.
